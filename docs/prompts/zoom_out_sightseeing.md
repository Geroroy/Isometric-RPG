# 축소 한계 넓히기 — 맵 풍경 구경용 (프롬프트)

isometric-rpg 리포에서 **화면 축소 한계를 맵 풍경을 둘러볼 수 있을 만큼 넓혀 줘.** 확대 한계(240줄, 사거리 7타일 적이 보일 것),
기본 배율(PC 세로 360줄), 캐릭터 스프라이트는 그대로 둔다. 근거는 `docs/prompts/zoom_limits.md`와 `tools/qa/zoomlimits.mjs`의 측정.

## 지금 한계와 그 이유

- 축소 한계: 세로 540 · 가로 1024 게임 픽셀(`renderer.js` `VIEW_LIMITS`). 1080p에서 2배까지.
- 이유는 하나: 유닛은 플레이어 주변 ±34타일 상자(`game.js` `updateActive`) 안에서만 갱신·그려진다. 화면이 이보다 크면 사람들이 화면
  안에서 생기고 사라진다(576줄부터 팝인). 프레임 시간은 540줄에서 기본의 1.06배라 한계가 아니었다.

## 목표 — "구경하기 적절한" 넓이

- 한 화면에 한 구역(상층 광장, 언더시티 광장·골목, 크리스토프시스 진지 하나)이 통째로, 주변 낭떠러지 너머 도시 배경과 함께 보일 것.
  기준: 레벨 폭의 약 절반이 보이는 넓이 — 세로 약 900~1080줄(1080p를 1배로 보는 정도).
- 흔한 화면 모두에서 지금보다 적어도 한 단계 더 축소될 것(1366×768, 1080p, 1080p 125%, 2560×1080, 1440p, 4K).
  한 단계도 안 늘어나는 화면이 있으면 이유를 적는다.

## 지켜야 할 것 (측정으로 확인)

1. **팝인 0.** 넓어진 화면 안에서 유닛이 생기거나 사라지면 안 된다. 활성 범위를 고정 상자 대신 **화면 기준**(실제 카메라가 보는
   사각형 + 스프라이트 여유)으로도 넓힌다 — 화면에 보이는 유닛은 갱신·그려진다. 여러 경로를 걸으며 rows별로 센다(16:9, 21:9, 4:3).
2. **성능.** 프레임 시간(렌더러 + 후처리)을 rows별로 재고, 새 한계에서 기본(360줄)의 몇 배인지 기록한다. 소프트웨어 렌더라 절댓값은
   참고용이고, 비율이 기본의 3배를 넘으면 한계를 줄이거나 원인을 줄인다. 활성 유닛 수 증가(크리스토프시스 진지)도 기록.
3. **배경이 이어질 것.** 낭떠러지 너머 배경(`cityBackdrop.js`, 건물 프로토타입 `buildingBackdrop.js`)의 반복 타일이 화면보다
   작으면 같은 무늬가 한 화면에 두 번 보인다. 타일을 가장 넓은 화면(1920×1080 게임 픽셀)보다 크게 하고 메모리를 기록한다.
4. **카메라.** 화면이 레벨보다 넓어질 때 카메라 고정(`camRegions`)이 떨리거나 튀지 않을 것. 맵 바깥이 화면의 몇 %인지 기록.
5. **가독성.** 1배(게임 픽셀 = 화면 픽셀)에서도 캐릭터(약 52px)와 이름표·체력 막대가 알아볼 만할 것. 스크린샷으로 확인.
6. 확대·축소 버튼, 저장된 줌, 타이틀·컷신 구도, 클릭 위치·선택이 그대로 맞을 것.

## 진행

1. 측정 스크립트(`tools/qa/zoomlimits.mjs`를 넓히거나 새로)로 rows 540·640·720·900·1080 각각의 팝인(새 활성 규칙 전/후), 프레임 시간,
   활성 유닛 수, 맵 바깥 비율, 레벨 중 보이는 면적 비율을 뽑는다.
2. 화면 기준 활성 범위를 넣고 다시 잰다. 기준을 모두 만족하는 가장 넓은 한계를 정한다(세로·가로 둘 다).
3. `VIEW_LIMITS`, 배경 타일 크기를 고치고, 화면별 단계 표(`tools/qa/zoomsteps.mjs`)를 다시 뽑는다.
4. 직접 플레이 확인: 최대 축소에서 상층·언더시티·크리스토프시스를 걸으며 여러 프레임 캡처(팝인·떨림·배경 이음매), 전투 한 번,
   클릭 이동·선택. 스모크 테스트.
5. README, `docs/GAME_DESIGN.md` 2.1.1의 수치를 고치고 커밋·푸시.
